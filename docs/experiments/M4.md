# M4：Native 跨节点快转与 kube-proxy 共存

2026-11-17 验收通过。两个独立 QEMU/KVM 内核，Ubuntu 26.04.1 / Linux 7.0.0-43-generic，K3s v1.37.2+k3s1，kube-proxy iptables 模式。使用项目 CNI、Agent 与正式 ABI 2 BPF ELF；没有 Calico/Cilium 转发程序。

执行 `python3 tests/kubernetes/native.py` 和 `python3 tests/datapath/fallback.py`。精简结果见 [Native](M4-results.json)、[能力降级](M4-fallback-results.json)；原始命令输出分别在 `build/m4` 和 `build/fallback`。测试工具最初通过远程 stdin 复制文件得到空文件，改用显式 base64 内容传输并复跑；失败记录不作为通过证据。

| 检查 | 实际结果 |
|---|---|
| 双向 Native UDP 新 tuple | 源/目标节点各增加 1 次 redirect 与 CT miss；接收 TTL=62，MAC、IPv4 checksum 正确；目标 fast-delivery 计数增加 |
| PodIP TCP | 双向 HTTP 成功；GSO/已跟踪报文可走慢路径，未宣称整个 TCP 长流均快转 |
| SVC-01/02/03 | 本地、远端、hairpin TCP/UDP；DNS UDP/TCP 成功，CT hit 与 Service 慢路径计数增加 |
| SVC-04 | 非 Pod netns 198.18.0.2 访问 Node2 NodePort，后端在 Node1；TCP/UDP 成功，后端看到 Node2 SNAT 地址 |
| SVC-05 | 8 秒 Service TCP reverse 长流期间将新连接后端 c 改为 b；旧连接持续，新 HTTP 命中 b，直连 c 同时成功；之后恢复 c |
| SVC-06 | M0 注入 CT 查询错误不 redirect；本次刻意使用不存在的 kfunc 名称，使正式 loader 自动装载无 CT 引用的 baseline ELF，fast_ready=0/features=0，PodIP/VIP 通信及防源地址伪造仍通过；M2 验证 fastReady 关闭 |
| SVC-07 | M0 真实 CT 原始/回复 tuple、DNAT/hairpin SNAT 与负面对照；本次 Native 入口 fresh tuple 的 CT miss 与 Service 回包 hit 分别被实际观察 |
| 恢复 | Agent 停止不拆内核转发，重启恢复 UID/ID/epoch；drop_mutation=0 |

NodePort 的外部客户端是隔离非 Pod namespace，非物理外部主机。两台 VM 内核独立，但共享物理 CPU 和 QEMU socket underlay；长流字节数只证明连接持续，不作为物理网络吞吐结论。当前 Agent 仍以 systemd 部署，DaemonSet 验收另行记录。

R1 的限定成果成立：自研接入与控制面、同/跨节点 TC 三层快转、Linux 慢路径，以及固定环境下 kube-proxy Service 共存。没有验证原生 nftables/IPVS 模式、任意第三方 NAT、非默认 conntrack zone 或 NetworkPolicy。
