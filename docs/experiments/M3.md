# M3：Agent 与真实 Kubernetes 集成

2026-11-16 通过。环境是两台独立 QEMU/KVM 来宾，各 2 vCPU、4 GiB，Ubuntu 26.04.1、Linux 7.0.0-43-generic。K3s v1.37.2+k3s1、containerd 2.3.7-k3s1；禁用 Flannel 和内置网络策略，保留 kube-proxy iptables 模式。两节点地址 192.168.77.11/.12；PodCIDR 10.244.0.0/24、10.244.1.0/24；ServiceCIDR 10.96.0.0/12。

本阶段 Agent 作为 VM 内的 systemd 宿主网络进程运行，采用独立只读 Node/Pod 的 ServiceAccount 凭据，通过 API Server 节点实际地址引导。DaemonSet 打包是后续交付工作，不能把此记录当作 DaemonSet 已验收。

## 实现与结果

- Node/Pod informer、节点路由计划、持久 ID/epoch、不可变快照、UDS root peer 身份检查、prepare/commit/delete/endpoint/status。
- CNI 在宿主 veth DOWN 时向 Agent prepare；挂载阻断程序后启用接口，Agent commit 安装/核验宿主路由、邻居和 Pod 配置，再开放 binding。
- 实际 containerd 确实传入 `K8S_POD_UID`。三个测试 Pod 的 runtime UID、Agent 记录和 API UID 一致；不等待 Pod.status.podIP 才完成 ADD。
- 两节点均 Ready；CoreDNS 正常运行。
- 同节点双向 PodIP HTTP 通信，redirect 和 delivery_fast_seen 均增长。
- 跨节点双向 PodIP HTTP 通信，此阶段通过 Linux Native 路由，不称为跨节点 BPF 快转。
- 本地后端、远端后端、hairpin 三类真实 ClusterIP，TCP HTTP 与 UDP echo 均通过；Service 分类和 CT 命中计数增长。
- 远端节点 Pod 通过 CoreDNS 查询 Service 域名，并访问返回的 ClusterIP。
- 停止 Agent 时，已固定内核对象仍使 PodIP/ClusterIP 可用；重启后同一 Pod UID、endpoint ID、epoch 恢复，通信正常。

测试入口 `tests/kubernetes/run.py`；原始结果 `build/m3/result.json`；精简结果 `M3-results.json`。测试镜像只使用现成 Python HTTP server、socat、iperf3 等流量工具，不增加独立 TCP 编程练习。初次测试发现 Alpine 基础镜像没有 `httpd`，补齐测试工具后通过。

`knd-test` 命名空间保留 a/b/c 三个演示 Pod 和 local/remote/hairpin 三个 Service，供后续 M4 使用。其他已有 kind 集群未修改。VM 使用 socket underlay，虽有独立 guest 内核，仍共享物理 CPU/内存；后续性能数据不能代表物理多机线速。
