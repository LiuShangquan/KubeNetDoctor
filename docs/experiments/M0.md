# M0 内核机制验收

日期：2026-11-16；内核及工具版本见 [环境报告](../environment.md)。测试源码是 `tests/m0/probe.c` 和 `tests/m0/run.py`，不是最终数据面。

## 实际通过的场景

- 双向 ICMP：12 次真实 `bpf_redirect`，接收 TTL=63；源/目标地址未改写。
- 对目标 veth egress 注入 DROP 后，重定向报文不能到达；撤销后恢复。
- PodIP 直连 UDP 与 iperf 的 TCP 控制连接成功，redirect 计数增加。
- 手工 iptables DNAT 夹具：TCP 反向传输、UDP 请求/回包正常；客户端的远端仍为 VIP；CT 原始方向和回包方向都有命中。
- 同端点 hairpin DNAT+SNAT 成功，双方向 CT 查询命中。
- **负面对照**：仅在隔离夹具中禁用 CT 保护，VIP 连接失败。这证明简单“PodIP 就快转”会破坏返回转换。
- 注入 CT 查询错误后，报文回退 Linux，连接成功且 redirect 计数不增加。
- 所有临时 namespace、服务器进程及私有 bpffs 挂载已回收；mutation_error 为 0。

精简机器结果见 [M0-results.json](M0-results.json)。完整命令/输出在 `build/m0/result.json`，客户端和服务端原始输出在同目录。

## 边界与偏差

这是单节点隔离内核夹具，尚不等同于 Kubernetes/kube-proxy、跨节点或正式性能验收。短暂 iperf 传输只验证路径正确性，不报告为项目性能成果。

探针为了用 ping 观察 TTL，允许 ICMP 快转；正式实现仍按照 v5 限定 TCP/UDP。故障注入开关只存在于测试探针中，不能作为生产配置。

runtime 实际传入的 Pod UID 必须在 M3 首次 Kubernetes/containerd 集成中抓取核查。当前 M0 没有新建集群，因此该检查随 runtime 集成执行；M1 使用明确的测试 UID，不宣称 runtime 参数已验证。
