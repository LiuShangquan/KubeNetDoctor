## 二、项目背景

在 Kubernetes 集群中，Pod 之间的通信可能涉及：

- Network Namespace
- veth Pair
- Linux TCP/IP Stack
- Cilium eBPF Datapath
- Routing / NAT
- Overlay / Underlay
- Host Network Interface

当业务出现 TCP 连接失败、重传或请求超时等问题时，单一观测源往往不能完整说明根因。

目前已经存在成熟工具：

1. Cilium/Hubble：网络流量、策略拒绝和协议事件。
2. Inspektor Gadget：TCP 重传、内核网络事件及容器信息关联。
3. Linux 网络工具：ss、ip、tc、ethtool 等。

我们不能忽视这些工具，更不能把重复实现已有功能包装为技术创新。

项目采用以下策略：

**复用 Hubble 的数据面可观测能力，但自主实现 Linux TCP eBPF 探针、Go Agent、连接归属分析和跨层事件关联。**

Inspektor Gadget 作为功能和性能对照基线，不作为项目主要实现的依赖。

我们自主实现的目的包括：

- 深入理解 TCP 重传相关内核机制。
- 掌握 eBPF Tracepoint、Map、Ring Buffer 和用户态事件消费。
- 解决内核连接事件到 Kubernetes Pod 的归属问题。
- 研究 Hubble 与内核事件在 NAT、时间窗口和不同观测点下的关联。
- 构建可解释、有证据支撑的诊断结果。

不要求全面优于成熟工具，但必须具有独立研发价值和明确的技术边界。

## 三、项目功能目标

### 1. TCP eBPF Probe

使用 C 编写运行在 Linux 内核中的 eBPF 程序。

优先研究 `tcp:tcp_retransmit_skb` Tracepoint。

需要实现：

- TCP 重传事件捕获。
- IPv4 地址及端口信息提取。
- 内核事件时间戳。
- 可获得的 Socket / Network Namespace / cgroup 相关信息。
- BPF Ring Buffer 事件上报。
- BPF Map 配置与过滤。
- 丢失事件和性能指标统计。

必须验证实际 Linux 内核中的 Tracepoint 字段、BTF 类型及 eBPF Verifier 兼容性。

不得直接假设某个内核字段必然存在。

尤其注意：

TCP 重传可能发生在内核定时器等上下文，current PID 不一定是应用进程 PID。

不能将 current PID 直接作为 Pod 归属的唯一依据。

### 2. Go Node Agent

使用 Go 开发节点级 eBPF Agent。

以 Kubernetes DaemonSet 部署。

技术：

- Go
- cilium/ebpf
- bpf2go
- gRPC
- Context
- Goroutine
- Channel
- Sync
- BPF Ring Buffer

需要实现：

- 加载和卸载 eBPF 程序。
- Tracepoint Attach/Detach。
- Ring Buffer 事件读取。
- 内核事件解码。
- Trace Session 创建、取消和超时。
- 多个追踪任务的并发控制。
- 事件过滤与限流。
- 有界内存缓冲。
- Agent 优雅退出和资源清理。
- Trace Session 状态及异常处理。
- Agent 内部指标。

首版只允许受控的诊断会话，不默认持续向 Manager 发送整个节点全部 TCP 事件。

需要明确设计：

多个诊断会话共享一个 eBPF Probe 时，BPF Map、事件过滤和会话管理如何避免相互干扰。

不得因为每个用户请求都重新加载独立探针而导致不可控的内核资源消耗。

### 3. Hubble Event Adapter

使用 Hubble Relay 的 Observer gRPC API 获取网络事件。

技术：

- Go
- gRPC
- Protobuf
- Hubble Observer API
- TLS / mTLS

需要实现：

- Relay 连接。
- GetFlows 流式消费。
- 相关 Pod 和 Namespace 过滤。
- TCP Flow 解析。
- Verdict 和 Drop Reason 解析。
- gRPC 连接断开及重试。
- Context 取消。
- 事件缓冲与背压。
- 数据丢失及采集不完整状态记录。

不要使用 Shell 调用 `hubble observe` 再解析终端文本作为核心接入方案。

不得假设 Hubble 保存了所有历史事件。

对于历史诊断数据，必须明确实际缓存及存储能力。

### 4. Kubernetes Metadata / Connection Mapper

使用 client-go 实现 Kubernetes 元数据缓存。

技术：

- client-go
- SharedInformer
- Indexer
- Lister
- Kubernetes API Machinery

需要关注：

- Pod
- Node
- Service
- EndpointSlice

建立以下映射关系：

- Pod IP → Pod UID
- Pod UID → Namespace / Pod Name
- Pod UID → Node
- Service → EndpointSlice → 后端 Pod
- 内核 TCP 连接 → Kubernetes Pod

核心难点：

1. Pod IP 可能被复用。
2. Pod 删除、重建时元数据会发生变化。
3. Hubble 和 eBPF 的事件时间可能不同。
4. NAT 可能导致五元组变化。
5. 内核事件不一定携带可直接使用的 Pod UID。
6. TCP 事件发生时的 PID 可能不代表真正的 Socket 所有者。

必须设计清晰的归属策略。

不能将无法确认的关联关系伪装成准确映射。

需要明确区分：

- Confirmed
- Probable
- Ambiguous
- Unknown

这些状态表示事件关联可信程度，不代表已经确定网络故障根因。

### 5. Connection Correlation Engine

自主实现跨层连接事件关联。

输入：

- Hubble Flow
- eBPF TCP Retransmission Events
- Kubernetes Metadata
- 必要的节点网络状态

使用以下信息进行关联：

- Source IP
- Destination IP
- Source Port
- Destination Port
- Network Namespace
- Socket / cgroup 信息（可用时）
- Node
- Pod UID
- Timestamp
- NAT 转换上下文（可验证时）

要求：

- 设计统一事件模型。
- 保留原始事件来源。
- 实现时间窗口匹配。
- 实现有界事件缓存。
- 处理重复事件。
- 处理事件到达延迟。
- 处理 Pod IP 复用。
- 处理事件丢失。
- 支持并发诊断任务。
- 避免无界 Goroutine 和 Channel。
- 保留无法可靠关联的事件。

需要为匹配算法编写独立单元测试。

特别注意 Hubble 与 eBPF 可能观察的是连接的不同阶段或 NAT 前后的地址，不能仅凭一个相同五元组就假定事件一定属于同一连接。

### 6. Diagnosis Engine + CLI

开发 Go 诊断引擎与 kubectl 插件。

CLI 使用 Cobra。

目标命令：

```
kubectl netdoctor diagnose --source default/client --destination default/server --duration 30s
```

执行过程：

1. 解析目标 Pod 和诊断请求。
2. 查询 Kubernetes Metadata。
3. 定位源 Pod 所属 Node。
4. 向对应 Agent 创建限时追踪任务。
5. 订阅相关 Hubble Flow。
6. 收集 eBPF TCP 重传事件。
7. 执行跨层连接关联。
8. 运行故障分析规则。
9. 输出诊断结果。

诊断报告必须包含：

- Observations：观测事实。
- Evidence：直接证据。
- Hypotheses：故障假设。
- Unknowns：缺少的证据。
- Recommendations：进一步排查建议。

严禁只根据 TCP 重传就判定物理网络丢包。

严禁将 Hubble 未观察到响应直接等同于数据包丢失。

## 四、总体架构

系统采用以下部署结构：

- Hubble Relay：现有网络观测基础设施。
- KubeNetDoctor Manager：Deployment。
- KubeNetDoctor Agent：DaemonSet。
- kubectl-netdoctor：客户端命令行插件。

主要数据流：

用户 CLI → Manager → Kubernetes Metadata 查询 → Trace Session 创建。

同时：

Hubble Relay → Hubble Adapter → Correlation Engine。

Linux TCP Stack → 自研 eBPF Probe → Ring Buffer → Go Agent → Correlation Engine。

最终：

Correlation Engine → Diagnosis Engine → Evidence Report → CLI。

Manager 和 Agent 之间的通信优先使用 gRPC。

首次实现时不要引入 Kafka、Redis、Elasticsearch、ClickHouse 或数据库。

可以采用有限时间窗口的内存缓存，并记录缓存和历史数据能力边界。
