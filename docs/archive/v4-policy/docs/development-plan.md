# 开发计划与学习安排

状态：实施前计划。用户可充分投入，学过 Go/C、熟悉 Linux 与网络理论，尚无网络编程项目经验；明确不安排独立 TCP 收发实验。投递日期尚未给定。

计划以每周约 5 个有效开发日估算，总计约 43–67 个开发日，即约 9–14 周量级；不是进度承诺，也不是要求固定每天工时。M0 完成后按实际编码、调试速度重估。完成一个阶段并通过验收，再进入下一个。

## 1. 里程碑

| 阶段 | 候选工作量 | 主要产物 | 验收与停下条件 |
|---|---|---|---|
| M0 环境与 TC 最小实验 | 3–5 日 | 环境锁定表、netns/veth 拓扑、最小 TC 程序、Map/lock/timer 能力记录 | 自身程序实际放行/丢弃指定流量；关键 helper 无法加载则先解决基线 |
| M1 单节点 CNI | 5–8 日 | CNI 入口、host-local 委托、netlink 配置与事务记录 | CNI-01/02/03/06；真实 netns 可用，失败后不留错误分配 |
| M2 TC ACL | 5–8 日 | 报文 parser、Map ABI、有限 ACL、动作与原因计数 | DP-01 至 DP-05；不能只打印报文而没有动作验证 |
| M3 策略编译与发布 | 5–8 日 | 选择器/规范化、完整 snapshot、版本发布协议 | POL-01 至 POL-05；规则语义有独立测试，容量失败明确 |
| M4 TCP 授权状态 | 8–12 日 | 状态转移实现、锁/timer回收、限制说明 | FLOW-01 至 FLOW-06；ACK绕过/身份复用/回收竞态未解决则停止 NetworkPolicy 宣称 |
| M5 Kubernetes/native 集成 | 7–10 日 | Agent 引导、端点协议、Node 路由、有限 NetworkPolicy、基础性能记录 | CNI-04/05、ID/CTRL/NET；跨节点真实连接受策略控制；保存单流 B0/B1/B2 初始数据 |
| M6 VXLAN 路径 | 5–8 日 | 静态 VTEP、路由/邻居/FDB 控制与模式配置 | VX-01/02；不做在线混合切换，内外层路径可解释 |
| M7 工程、性能与展示 | 5–8 日 | 回归、性能原始数据、优化实验、README/演示 | 同条件重复测试；支持边界与自主实现可核查 |

测试编号的唯一完整定义位于 [testing.md](testing.md)。各阶段不是都从零开始：之前的测试和代码随集成逐步复用。

## 2. 每阶段的第一项小任务

- M0：识别可运行的 Linux 环境，建立两个 netns 和一对 veth；用现成工具验证路径，然后挂一个能选择性 DROP 的 TC 程序。
- M1：只处理一份合法 CNI 配置和 VERSION，再逐步做 ADD/DEL；在实际网络资源创建前明确事务记录。
- M2：先解析 Ethernet/IPv4，不读取 TCP 之前先证明边界检查；随后加端口规则。
- M3：先写一个纯函数，把固定 Pod 标签集合与一条策略转为规范化允许项；再接 Map 发布。
- M4：先完成“一端发 SYN、对端 SYN-ACK、最终 ACK”的双向状态测试；再增加重传、关闭和并发。
- M5：先让真实 runtime 成功调用 CNI，并处理 PodIP 尚未回写的启动时序；再启用跨节点与策略管理。
- M6：先手工验证 routed VXLAN 的三类转发表，再把完全理解的配置转为 Go netlink 代码。
- M7：在 M5 初始数据上补齐 B0/B1/B2 负载矩阵与重复测量，再决定是否以及如何优化。

## 3. 与实现绑定的知识点

| 阶段 | 必须能够解释 |
|---|---|
| M0–M1 | netns 与线程、veth 两端、TC 方向、ARP/路由、CNI 调用时机、IPAM 与网段分配区别 |
| M2 | skb、线性/非线性缓冲、字节序、IHL/DOFF、GSO/GRO、verifier、TC 动作 |
| M3 | selector 逻辑、规则并集、数据结构、map-in-map、读写并发、局部与全局一致性 |
| M4 | SYN/ACK/FIN/RST、授权与 TCP 协议状态的区别、tuple复用、锁、timer、内核资源上限 |
| M5 | Informer/Workqueue、不可变编译输入、启动依赖、端点身份、控制面与数据面故障区别 |
| M6 | Underlay/Overlay、VTEP、路由/邻居/FDB 各自职责、封装开销、MTU与回程 |
| M7 | 瓶颈剖析、测量噪声、基线、吞吐与时延分布、性能和功能取舍 |

每次讲解围绕即将写的代码，避免提前铺设不相关课程。用户已掌握的理论不重复讲成入门课；通过解释实际报文路径和代码中的边界来确认理解。

## 4. 范围削减规则

- M3 完成后可以交付 R0，必须写清楚是 CNI/ACL 原型，尚未有完整返回流与 NetworkPolicy 适配。
- M5 完成后交付 R1；有原生路径、限定入站策略、生命周期与基础性能证据。
- M6–M7 完成 R2，对应 JD 的 Underlay/Overlay 和性能实验更充分。
- 如果投递时间提前，优先交付已经验收的 R0/R1，不跳过状态正确性、失败回滚或编造性能。
- 首先删除自动混合选路、其他协议、Service NAT/LB、eBPF 转发加速、DPDK、GPU/RDMA和独立诊断平台等扩展；不得以减少关键反例测试来省时间。

## 5. 开源阅读与工程记录

在对应阶段选择固定 release/commit 阅读 CNI 规范与插件、Flannel native/VXLAN 控制路径、Cilium TC/策略思路、cilium/ebpf 加载示例。每次记录“输入、状态、内核对象、错误处理、与本项目差异”，不以读过整个仓库作为进度。

若发现可复现的上游问题，可以另行整理 issue/测试/修复建议；发布和对外联系按用户明确授权执行。开源贡献不作为本项目能够结束的外部依赖，也不保证合入。

实施后的阶段报告包含：目标、主要代码、关键机制、实际测试、失败/限制、与设计偏差、下一步。阶段开始先检查现有代码与工作区，再进行小范围实现。
