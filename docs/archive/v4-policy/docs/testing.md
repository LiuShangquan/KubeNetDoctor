# 测试、性能与验收计划

状态：尚未执行。本文只定义验收方法与候选门槛；不存在“已通过”结果。阶段对应 [development-plan.md](development-plan.md)。

## 1. 验证分层

| 层次 | 工具/方法 | 可以证明 | 不能代替 |
|---|---|---|---|
| Go 纯逻辑 | 表驱动、性质测试、race | selector、编译、差异计划、并发管理逻辑 | 真实 CNI/netlink/eBPF |
| BPF 包向量 | 目标内核 BPF_PROG_TEST_RUN，先核查支持 | 解析、Map 查询、动作和部分状态转移 | 实际 hook 路径、全部 offload/非线性行为 |
| Linux netns | veth/bridge + 现成收发工具 | hook 方向、CNI、状态、失败回滚 | Kubernetes runtime 集成 |
| Kubernetes E2E | 固定版本集群、真实 Pod/NetworkPolicy | runtime 调用、元数据变更、跨节点行为 | 千节点生产规模 |
| 独立内核性能 | 固定 VM/物理节点、重复 A/B | 特定条件下的开销与瓶颈 | 未测试硬件或 GPU/RDMA 性能 |

不安排独立的 TCP 收发程序练习，也不开发通用压测平台。优先用 socat/nc、iperf3、netperf、tcpdump、bpftool 和 iproute2；先核查实际安装版本与功能。TCP 握手/异常包序列可用测试专用报文生成工具，不作为用户需要先完成的应用开发项目。

## 3. 测试时序与真值

开始测试前保存：配置、拓扑、内核/工具版本、测试参数、代码 commit、对象 UID/resourceVersion 和 applied generation。

策略写入 API 后，分别等待相关节点报告包含该对象版本的快照并读回确认，再发送“生效后”用例。另设一组专门测量传播期行为，不能将两种结果混在一起。

跨节点延迟测量使用同一测试客户端的单调时钟，记录 API 更新响应到轮询发现 applied 的时间及轮询间隔/网络往返误差；它是观察到的生效上界，不是精确内核切换时刻。

授权判定以测试定义的规则与发送/接收结果为主，BPF 计数、有限事件、抓包和 Map 内容作为交叉证据。原因计数不能独自证明所有报文均按预期到达。

故障注入只作用于隔离环境与项目资源，每项保存恢复步骤。对 CNI 故障、Map 失败和规则发布使用故障点；对网络路径使用受控路由/FDB删除或 tc/netem。注入位置与参数只由测试程序保存，不传给被测逻辑当作答案。

## 4. 性能实验

### 4.1 基线

| 组 | 数据路径 | 目的 |
|---|---|---|
| B0 | 同一网络，不挂策略程序 | 基础网络能力 |
| B1 | 挂程序，解析并允许支持流量，无策略状态查询 | 最小 hook/解析开销 |
| B2 | 完整规则匹配与 TCP 授权状态 | 实际功能开销 |
| B3 | 基于剖析提出的一项优化，语义保持一致 | 验证优化收益与代价 |

B1 明确是测量模式，不可冒充完整策略实现。native 与 VXLAN 各执行 B0–B2；只在必要组合上执行 B3，避免无意义穷举。

### 4.2 负载与测量

- iperf3 长连接吞吐：1/8/32 并发流，正向与反向；应用写入块大小不等于线上包长。
- netperf TCP_RR 类请求/响应测量时延，TCP_CRR 类测试测新连接处理能力；工具不可用时先记录等价替代方案与语义，不能直接拿 ICMP RTT 代替 TCP 策略延迟。
- 身份/规则规模候选 16/64/256 peer，允许项规模逐步增加至容量；这些是编译/Map压力规模，不等于已有同等数量物理节点。
- CPU、RSS、Map 内存、softirq、丢弃原因、状态容量、规则构建和发布耗时同步记录。
- 固定 CPU/网卡/MTU/offload、TCP 参数、服务进程与拓扑，随机化或交替 A/B 顺序。
- 候选每组预热 10 秒、采样至少 60 秒、独立重复 5 次；高波动时先排查环境再增样，不挑最好一轮。
- 延迟工具能给出分布才报告 p50/p95/p99；只返回均值的工具不能生成伪分位数。

所有配置在实验开始前保存。并发、规则规模、MTU或 offload 改变时必须分组，不能把多个变量一起变化后将结果归功于某项优化。

### 4.3 优化完成标准

至少完成一次“剖析证据 → 假设 → 单项修改 → 同条件对照 → 结论”的闭环。例如减少重复快照查询、压缩规则展开、优化锁争用或减少每包调试开销；具体选哪项由实测决定。

收益不显著也是有效实验结论。只有重复数据支持且功能回归通过，才能保留优化并写入成果；不能因为使用 eBPF 就宣称吞吐提升。

## 5. 资源和通过门槛

初始候选目标：单 Agent 用户态 RSS 上限 256 MiB、项目 BPF Map 总预算 128 MiB、debug Ring Buffer 1 MiB。先在 ENV 阶段测量可用资源与 Map 预分配开销，再冻结适用规模；超预算要减小明确配置或改进实现，不静默突破上限。

在声明规模内，正常稳态策略更新候选观察上界 5 秒；这不是实测结果。M3 建立基线后冻结门槛与硬件条件，后续改动不能为“通过”临时放宽标准。

允许/拒绝与状态转移正确性是硬门槛；性能默认没有预先许诺的提升百分比。并发/取消/恢复测试不得遗留无界 goroutine、队列或持续增长资源。

## 6. 结果归档

实施后每组实验在 `docs/experiments/<编号>/` 保存 manifest、环境清单、运行命令、原始输出、统计脚本、关键抓包摘要、结论和限制。只保存必要报文信息，不采集无关业务流量。

阶段报告明确：已运行、未运行、失败、环境阻塞分别是什么。Mock 通过不能写成内核通过；kind 结果不能写成独立多节点性能；独立 VM 也不能写成千节点/GPU 生产经验。
